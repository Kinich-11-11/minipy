## 1. 根因与独立机制

复现：`m=[[0]*3]*3; m[0][1]=5`。原候选得到 `[[0,5,0],[0,0,0],[0,0,0]]`，CPython 三行均是 `[0,5,0]`。`listlit/packRef827` 已将内部 L/D 转为 `!/&` 引用编号，`rightside` 的乘法循环重复的是同一份编码；`listitem/indexget` 可以解引用。`m[0].append(8)` 本来就能正确更新共享行，因此根因不在乘法算法。旧 `pathset` 在嵌套赋值时只把临时 `__pw` 改后的内容递归写回一个父槽位，丢失了共享引用的语义；对于提前退出分支，其 `w7dep` 未减一、暂存名字也未清理，后续 RUN 继续受影响。

新增 `nested-reference-writeback`（`after: []`，写集 `heap.nested-index-writeback`、`path.state`、`RUN.pathState`，适用精确原核心 SHA）：

- 接收者为已经索引的 L/D，且 `valueRef827`、`itemRef827` 一致且为正，才保留该引用编号；在原接收者求值前清零旧结果。使用原有 `VStack` 跨临时下标赋值暂存编号，在错误分支前弹回。
- 临时 `indexset` 完成后，原位写 `RefData826`，不替换父容器内携带编号的槽位。没有已证实的引用时保留旧递归写回。槽位重绑与子对象修改因此不同。
- 若该 ID 有名称绑定，匹配 `RefIds826`，拆解现有作用域键，以 `refFind826` 核对当前精确绑定行和 ID，再复用 `assign/publish` 同步活跃绑定；不会扫描所有值并按序列化内容等同对象。扫描仅在该引用确实有名称映射时启用；现有作用域索引最坏仍为线性，不做缓存或全堆重写。
- 正常及所有已有提前退出共 8 个退出点通过共享 `path leave` 清理；新的 RUN 从零初始化路径深度、路径回写标志和 `VStack`。保留对普通控制流和异常的原有处理，不以宿主语言执行 Python。

选择该方案是因为复用已存在的引用表而非新增重复的别名协议。未尝试按列表内容同步所有相等的对象；两个独立而相等的子列表必须仍然彼此隔离。字典内部尚未编码引用的值、删除以及参数直接传递属于不同路径，不能靠本补丁宣称解决。阶段 02 可独立从锁定核心构建；累计候选指定阶段 01、02，两者无重复写职责。

## 4. 验收边界与后续

阶段 02 累计候选仍使用锁定的 v5 SHA 和独立补丁，不重放 v4 的历史补丁，不改 core-lock。`summary.json` 同工具链逐行比较阶段 01/02 历史 RUN，并区分新增专项；`live-diff-triage.json` 跟踪冻结原差分的逐项处置。第二 VM 源码入口在当前环境缺少 `@turbowarp/jszip` 依赖，未测试；实际 Scratch/CCW 编辑器 UI 仍未实测，故按清单不提升基座、不宣布完成最终验收。

建议下一项：嵌套删除和共享子对象参数传递，或字典值引用的编码边界；字典视图 `repr/str` 和迭代器仍未修；再处理递归排列、`map/filter` 组合与作用域热点。优化前保持单一机制和明确验收账本，避免就地合并不相干改动。
