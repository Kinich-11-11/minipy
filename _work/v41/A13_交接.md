# A13（嵌套容器字面量）交接说明

> 目的：把 22–29 轮的全部结论压缩成一页，让接手者在 2–3 次构建内把 A13（并连带 A12 字典）修好。

## 一、现象与最小用例

| 写法 | 结果 |
|---|---|
| `x = [[1]]` | 通过 |
| `x = [1, [2]]` | 通过 |
| `x = [[1], 2]` | 报 `SyntaxError: parentheses` |
| `print([[1, 2], [3, 4]])` | 报 `SyntaxError: parentheses` |
| `print([1, [2, [3, 4]]])` | 能出结果但值错（`[1, 2]`） |
| `x = ([1], 2)`（外层用圆括号） | **通过**（可作临时绕行写法） |

触发条件 = **前导嵌套 + 顶层逗号**；词法层正常（Tok/Kind 均已验证）。

## 二、三个根因（都已用实验确认，按发现顺序）

1. **共享全局列表被内层调用清空**（第 27 轮）。`listlit` 用全局 `LComm`/`LOut`，元素求值会递归进入 `listlit`，
   内层开头的 `clear(LComm)/clear(LOut)` 抹掉外层的表；外层随后 `lplo = item(lpi) of LComm + 1` 取到空串 → `lplo = 1`，
   尾段发出 `eval(1, 8)`（探针实测），深度以 1 结束 → `parentheses`。
2. **逗号扫描把区间首括号计入深度**（第 28 轮）。嵌套时 listlit 收到的区间形如 `[1, 2], [3, 4]`，首字符是内层 `[`，
   于是顶层逗号被算成深度 1、一个都记录不到 → 元素循环不跑、整段被当单元素求值。修法：游标在首记号是 `[`/`(`/`{` 时从 `lo+1` 起步。
3. **元素计数/切片起点**（第 28 轮发现，尚未定位）。把 1、2 都修好后仍有错误，怀疑 `l2oc`（本层元素数）或 `l2bo + l2pi`（本层切片起点）算错，
   或尾段被重复求值。

## 四、建议的第一步（一次运行就能判定）

在 `p42.txt` 的 `listlit2` 内加打印：

```
addTo("Output", "IN lo/hi/bc/bo=" + lo + "/" + hi + "/" + l2bc + "/" + l2bo)
addTo("Output", "SCAN cnt=" + l2cnt)              // 扫描后
addTo("Output", "LOOP pi/oc=" + l2pi + "/" + l2oc) // 循环内 append 之后
addTo("Output", "LEN LOut=" + length of LOut)
```

跑 `print([1, [2, [3, 4]]])`，对照期望（外层：lo/hi 正确、cnt=1、oc=2），即可区分是「计数错」还是「取值错」。

若计数正确而值错 → 看 `l2bo + l2pi` 切片与尾段是否重复 append；
若计数错 → 问题在扫描的起点跳过或 push/pop 变量集。

## 五、更稳的替代方案（推荐给时间紧的情况）

放弃"只动自己那一段"的巧劲，改用笨办法：`listlit` 入口把 `LComm`/`LOut` 的**全部内容**压到 `VStack`（先压长度再压元素，
利用 VStack 元素是独立字符串、可容纳带 lsep 的编码串），返回前按长度整体恢复。P28 对累加器用过同样手法，可靠但方块多。

修好后请一并回归：`nested.json`、`tuple.json`、`comp.json`、`gaps.json`、`regress.json`，并重建 v4.10–v4.23 产物比对。

## 七、第 31 轮：静态依赖扫描结果（新增工具 `who.cjs` / `who2.cjs`）

对**构建后的产物**做静态扫描（比反编译可靠），得到：

* 读写 `LComm` / `LOut` 的过程只有三处：`listlit`（自身的扫描/循环/连接）**以及** `fpush` / `fpop`（P14 的帧保存/恢复把它们也算进了保存集）。
* `fpush` / `fpop` 的调用者**只有 `calluser`**（用户函数调用），所以普通语句里的列表字面量不会触发帧保存——第 30 轮 P43 的失败**不是** fpush/fpop 干扰。
  但要注意：**在用户函数里写嵌套字面量**时，fpush/fpop 会额外保存/恢复这两个表，属于潜在坑点。
* `listlit` 的调用者只有 `eval` 一处。
* `tokenize` 的调用者：`prepare`（4 处）、`calluser`（3 处）、**`fstr`**、**`atom`** —— 后两者会在表达式求值过程中**重建 `Tok`/`Kind`**，
  这正是交接文档第 6 节要验证的"假设 1"：如果嵌套求值路径上有 re-tokenize，外层 listlit 之后再回到 eval 分派时看到的 `Tok` 可能已经不是同一条语句的。

**结论**：P42/P43 的失败无法用"共享表被清空"或"扫描差一"单独解释，也无法用 fpush/fpop 解释；下一步必须先做运行时插桩，
重点盯两件事：(a) 嵌套求值期间 `Tok`/`Kind` 是否被重建（在 `tokenize` 入口打印调用者与行号）；(b) `LComm`/`LOut` 在进入/离开每次 listlit 时的长度。
这两条打印各一次运行即可定论。

## 八、第 32 轮：因果链已用探针完整证实（P44）

探针：`tokenize` 入口打印 `pc` 与源串；`listlit` 入口/出口打印 `lo/hi` 与 `LComm`/`LOut` 长度。跑 `x = [[1], 2]` 得到：

```
TOK pc=1 src=x = [[1], 2]        （同一源串被 tokenize 了 3 次，Tok 内容稳定，非本问题）
LITIN  lo=4 hi=8 LComm=0 LOut=0   （外层 listlit 开始）
LITIN  lo=5 hi=5 LComm=1 LOut=0   （元素 1 求值 → 递归进入内层 listlit；此时外层已记录 1 个逗号）
LITOUT LComm=0 LOut=1 ev=<lsep>N1 （内层返回：**LComm 被清成 0**，外层的逗号表丢了；LOut 留下内层元素）
Line 1: SyntaxError: parentheses
```

**这就是完整因果链**：内层 `listlit` 的 `clear(LComm)` 抹掉外层的逗号表 → 外层循环里 `lplo = item(lpi) of LComm + 1` 取到空串 → `lplo = 1`
→ 外层尾段发出 `eval(1, 8)`（与第 24 轮探针完全一致）→ 深度以 1 结束 → `parentheses`。
外层再也不会打印自己的 `LITOUT`（异常在尾段抛出）。

## 九、两次修复尝试都失败（P43 / P45），但失败点已不同

* **P43**（整表压栈/恢复的 `listlit3`）：构建正常，但 `[[1,2],[3,4]]`、`[[1],2]` 报 parentheses、`[1,[2,[3,4]]]` 无输出。
* **P45**（在原有 `listlit` 的两处递归 eval 前后插 save/restore，不改算法）：构建正常（9,484 块），但**连普通列表也坏了**（nested2 仅 1/10 通过）。
* 两次都用了同一套"按长度压栈/恢复列表"的辅助代码 ⇒ **嫌疑集中在这段辅助代码本身**，而不是算法思路。
  需要重点检查：
  1. 恢复时读取栈内元素的位置算式 `len - n + (i-1)`（以及删栈时 `n+1` 的边界）；
  2. `VStack` 是否被 `listfmt` / `tupfmt` / `tuplelit` 在同一段时间内使用（若它们的压/弹不平衡，会读错栈）；
  3. `STOPTHIS`（出错提前返回）路径上未弹出，导致栈泄漏。

**建议**：把"列表压栈/恢复"单独做成两个过程并先用最小用例验证（例如 `a=[1,2]` → 手动压栈 → 清空 → 恢复 → `print(a)`），
确认这段辅助逻辑本身正确后，再套回 `listlit`。这一步比继续改 `listlit` 更省时间。
